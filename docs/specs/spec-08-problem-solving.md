# 问题排查纪律与决策流程

## 标准决策流程

```
[需求输入] → [分析现有代码] → [有疑问?]
                                  ├─ 是 → [查 Library/PackageCache 包源码 + 代码图谱]
                                  │         ├─ 找到 → [分析方案]
                                  │         └─ 没找到 → [抛出问题给用户]
                                  │                      └─ 用户也解决不了 → [按知识库开发并标注未验证]
                                  └─ 否 → [方案明确?]
                                            ├─ 是 + 影响小 → [直接实施]
                                            ├─ 是 + 影响大 → [出方案等确认 → 实施]
                                            └─ 否 → [提问确认 → 实施]
```

## 核心规则

### 1. 不能凭猜想直接改代码

- **禁止**：凭经验猜原因，直接改代码试。
- **必须**：
  1. 先定位根因——读相关源码、追调用链、看 Unity Console 日志与 `Logs/`、加必要的临时 `Debug.Log`。
  2. 定位不到就继续取证据（扩大读取范围、用代码图谱追调用关系），而不是换一种猜法改代码。
  3. 给出修复思路、影响范围、预期效果。
  4. 用户同意 → 改 → 验证。

### 2. 不确定时必须确认

出现以下任一情况先提问：

- 需求存在多种合理解释
- 实现有两条以上路径且影响范围差别明显
- 要确认接口能力、命名、配置结构、资产归属
- 涉及架构级决策（新子系统、asmdef、输入方案、UI 技术栈）
- 不确定某个现有模式是否适用于当前场景

### 3. 查证顺序

1. 工程源码 `Assets/Scripts/`
2. 实际安装包源码 `Library/PackageCache/<pkg>/`（版本敏感 API 的唯一权威）
3. 代码图谱（codegraph `explore` / CBM `search_graph`、`trace_path`）
4. 以上都无答案 → 停下提问

Unity 官方文档与网上示例仅作线索，与 `PackageCache` 冲突时以 `PackageCache` 为准。

### 4. 最小改动

- 优先局部修改、优先复用现有结构。
- 只在现有结构确实无法承载需求时才新增方法/类/模块。
- 不为「更优雅」大面积重构；不为「看起来完整」加用不到的抽象层。

### 5. 验证优先

每次修改后必须验证，能不用 Editor 就不用（详见 [spec-09-build-verify.md](spec-09-build-verify.md)）：

| 层次 | 手段 | 适用 |
| --- | --- | --- |
| 编译 | `dotnet build Assembly-CSharp.csproj` | 全部代码改动，最快 |
| Editor 编译 | Unity `-batchmode -quit` 批处理 | 需要 Editor 侧确认时（需先关 Editor） |
| 单测 | Test Framework `-runTests` | 有测试用例时 |
| 实机 | Unity MCP 工具 | 场景/Prefab/资产/实机行为 |

无法完成完整验证时必须说明：哪些已验证、哪些未验证、未验证的原因。

## 典型场景

### 场景 A：Bug 修复

```
1. 明确现象、触发条件、复现步骤、相关代码位置
2. 定位根因（源码 + 图谱 + 日志）
3. 给出：修复思路 / 影响范围 / 预期效果
4. 用户同意 → 实施 → 编译验证 → 汇报
```

### 场景 B：新功能

```
1. 先查现有结构里是否已有可复用入口（状态机、单例、MonoManager、输入、准星配置）
2. 优先扩展而不是新起一套
3. 说明方案选择理由与影响面
4. 用户同意 → 实施 → 验证核心流程
```

### 场景 C：代码分析

```
1. 优先 codegraph explore / CBM search_graph，其次 grep
2. 搜索跳过 Library/、Temp/、obj/、Logs/、UserSettings/ 与三个大型第三方资源目录
3. 不确定的结论明确标注「待确认」，不写成既定事实
```

### 场景 D：不确定 API 是否存在

```
1. 在 Library/PackageCache/<pkg>/ 中搜类与方法签名
2. 图谱追调用关系确认是否有现成用法
3. 找不到 → 停下提问：「我在 <包名>@<版本> 源码中未找到 XXX，不确定是否存在。」
4. 用户也不知道 → 按知识库给方案，并标注假设条件与未验证项
```

### 场景 E：Unity 未打开 / MCP 不可用

```
1. 如实声明「实机未验证」，不假装跑过
2. 列出需在 Editor 手动确认的具体项（用清单，不写成模糊的「请自行测试」）
3. 提供可离线完成的替代验证（编译信号）
```

## 禁止行为清单

| 禁止 | 原因 |
| --- | --- |
| 凭猜测直接改代码 | 掩盖根因，引入新问题 |
| 凭记忆写版本敏感 API | CM 3.x / Input System 1.14 与网上示例差异大 |
| 不确定时擅自选方案 | 可能偏离意图 |
| 整文件重写而非局部修改 | 风险高，不利回溯 |
| 改完不验证、不说明未验证项 | 无法确认正确性 |
| 手改 `.unity` / `.prefab` / `.asset` / `ProjectSettings` | 会损坏资产（见 spec-00 铁律 5） |
| 写入 `Library/`、`Temp/`、`obj/`、第三方资产目录 | 只读参考 |
