# 核心铁律与编码纪律

本册是全工程最高约束。与其他分册冲突时以本册为准。

## 铁律

### 1. 禁止臆造 Unity 与包 API

遇到下列情况必须停下，不准凭模型记忆输出：

- 不确定某个 Unity / URP / Cinemachine / Input System / Animation Rigging API 的签名
- 不确定某方法在当前包版本下是否存在或已被弃用
- 不确定生命周期回调或事件的触发时机

正确流程：

1. 用代码图谱（codegraph / CBM）或读源码确认。引擎侧一律以 `Library/PackageCache/` 里**实际安装的包源码**为准，它的优先级高于任何官方文档与网上示例。
2. 图谱与包源码都查不到，把问题抛出给用户等待确认。
3. 只有用户也表示无法解决时，才按模型知识开发，并在汇报中显式标注「未经源码验证」。

> 本工程版本敏感：Cinemachine **3.1.7**、Input System **1.14.0**、URP **16.0.6**、Unity **2023.2.20f1**。网上绝大多数示例对应 CM 2.x / Input System 1.0.x，直接照搬必然报错。

### 2. 先分析 → 再确认 → 再实施

```
[分析] → [需求不明确则提问] → [方案确认] → [实施] → [验证] → [汇报]
```

- 需求存在多种解释、方案存在分歧、影响面大或不可逆时，先出方案等用户确认。
- 未经确认不得批量修改、整体重构、擅自扩展实现范围。
- 用户说「先分析」＝分块产出分析结论，不是授权无限检索。

### 3. 第三方资产只读

`Assets/Low Poly FPS Pack/`（296.2 MB）、`Assets/MMD4Mecanim/`（448.6 MB）、`Assets/Plugins/`（37.7 MB，含 EffectCore、YSA Toon、Roslyn）一律不修改其源码与资源。需要定制时，把资源复制到工程自己的目录再改。

### 4. 生成文件不手改

`Assets/Settings/InputSystem/MyInputSystem.cs` 由同目录 `MyInputSystem.inputactions` 生成。改输入一律改 `.inputactions`，由 Editor 重新生成；不直接编辑生成类。

### 5. 不手写 Unity 序列化 YAML

`.unity` / `.prefab` / `.asset` / `ProjectSettings/*.asset` 一律经 Unity Editor 修改（可用 Unity MCP 工具驱动），不手工编辑文本。手工改 GUID、fileID、缩进会直接损坏资产。

### 6. `.meta` 与资源同增同删

新增或删除资源时同步新增或清理对应 `.meta`，不留孤儿 meta；不修改已有 meta 的 GUID。

### 7. 最小改动

优先局部修改、优先复用现有结构，只在现有结构确实无法承载需求时才新增方法/类/文件。不为了「看起来更完整」堆抽象层、接口或冗余方法。

### 8. 本地事实来源优先级

1. 本工程当前源码：`Assets/Scripts/`、`Assets/Settings/`、`ProjectSettings/`
2. 实际安装的包源码：`Library/PackageCache/`（只读，真实生效版本）
3. 包自带文档：`Library/PackageCache/<pkg>/Documentation~`、`README.md`
4. 以上都没有答案时提问用户，不用模型记忆替代

`Library/`、`Temp/`、`obj/`、`Logs/`、`UserSettings/` 均为引擎生成的本地目录，只读参考、不写入、不入库。

### 9. 任务分级与流程深度

动手前先判定规模，走对应通道。分级只控制流程深度，不豁免本册铁律。

| 通道 | 判定 | 流程 |
|------|------|------|
| 轻量 | ≤1 个源文件、纯配置调整、修 Bug、改数值或文案，且不涉及状态机结构、输入动作、Prefab/场景结构、包体 | 直接实现交付，不写计划，单步推理收敛到能作答即止 |
| 常规 | 其余（新增功能、新增状态、跨域改动、机制调整） | 先需求对齐，再给文件级计划，再实施 |
| 大型 | 新系统骨架、存档/联机、多系统联调、URP 管线或资源体系改造 | 需求对齐后写计划，拆成可独立验证的子任务分步推进 |

**收敛约束**：常规及以上任务，单步内纯论证而无新信息、无工具调用、无结论产出时立即收敛——给结论／调工具／提问三选一，禁止同一问题反复论证。

### 10. 执行节奏与汇报

约每 3-5 个工具调用或 1-2 分钟无可见输出时，输出 1-2 行进度（在查什么／发现什么／下一步）。每轮交付收尾统一汇报：**验证方式 → 验证结果 → 尚未验证项 → 改动文件清单**。

### 11. 检索预算

同一目标检索 3-4 次仍无果、或方向不确定时，停下问用户，不继续扩大搜索面。可查证的事实（代码位置、当前行为、资产归属）自己查，不拿事实问用户；用户已给出答案或方向时直接采信执行。

### 12. 文档纪律

未获授权不新建或修改 `.md` / `.txt` 文档。`docs/` 是治理白名单区，只在明确要求时写入。不新建「说明／总结／设计」类散文档；长期结论写进 `docs/specs/` 对应分册的变更记录。
